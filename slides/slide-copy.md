## MAIN 02 / 第 3 頁：問題
**叫車是動作，出門才是需求。**
- 「先決定要叫車，才想到打開 App」是切入的產品假說，**不是已測的行為統計**。
- 待解決決策：「幾點出發？」行程／雨勢／轉乘；「搭什麼？」捷運、步行或叫車中立排序。
- 視覺：深綠「現在常見旅程」卡 + 時機、選擇兩張白卡。
- 依據：產品 brief 與 [yoxi 既有乘客流程](https://www.yoxi.app/passenger-tutorial)。

## MAIN 03 / 第 4 頁：初期人物
**先服務每天都在換交通方式的人。**
- 都市學生／通勤者（待研究的客群假設）；兼用捷運、公車、步行與叫車。
- 三種 JTBD：① 18:30 到捷運巨蛋站、希望不淋雨；② 遇到可信重大異動重新規劃；③ 沒有叫車需求也想找地方讀書。
- 同意授權可享情境建議；拒絕授權仍能手動使用。
- 視覺：角色大卡＋三張 JTBD 卡。依據：`docs/PRODUCT_BRIEF.md`。

## MAIN 04 / 第 5 頁：核心體驗閉環
**通知，不是對話的中斷；是對話的開始。**
1. 情境符合：行程 × 選擇同意 × 可靠資料。
2. 規則先過關：靜音、去重、冷卻、資料時效。
3. 點通知直接進入**同一段原對話**，能看到發送理由。
4. 可信卡片公平比較交通方式；高風險叫車與付款由使用者確認。
- 保留「直接叫車」熟悉捷徑；不需 AI 才能完成既有任務。
- 視覺：四段流程箭頭；強調第三段。依據：產品 brief / architecture。

## MAIN 05 / 第 6 頁：情境 A — 出發前
**18:30 到高雄巨蛋，先比較，再決定。**
- 地點明確為**高雄巨蛋／捷運巨蛋站**，不是凹子底。
- 使用者授權提醒；通知轉為原對話第一句；捷運＋步行與 yoxi 兩張卡。
- **雨勢、28／17 分鐘、NT$35／NT$240 和所有交通資訊 [模擬]，非任何實際費率、ETA、派車或即時 API。**

- 講者：公平比較，比強制推 taxi 更能建立信任。

## MAIN 06 / 第 7 頁：情境 A — 偏好改變

- 真正叫車必須返回官方控制流程看清接送點與費用，再由使用者確認；**無自動派車**。

- 講者：AI 可以理解人，但不能替人決定高風險行動。

## MAIN 07 / 第 8 頁：兩種其他高頻情境
**不叫車的那天，也應該有用。**
- B 異動：在可信事件、同意、過濾規則下，一次通知與改道卡；可忽略、稍後再說。
- C 無叫車意圖：「有兩小時，想找安靜地方」，候選學習場所和交通方式，步行／捷運更合適就不推薦叫車。
- 以上兩幕僅為**提案故事板**，不是 Team B HTML 原型已完成的額外實作。
- 視覺：黑白雙場景卡。依據：產品 brief。

## MAIN 08 / 第 9 頁：保留易用性
**熟悉的叫車入口，不能被 AI 藏起來。**
- 「直接叫車」「回家」「常用地點」應可不必聊天直接操作。
- 有資料才提供來源、更新時間的結果，權限不同意或失敗時可手動。
- 使用者能關閉提醒、設定靜音、重新排序；無資料時不顯示像真的即時數字。
- 視覺：對話首頁概念線框＋「快／清楚／可控／可退」四條 UX 原則。
- 依據：yoxi tutorial；產品 brief。首頁線框**改編** Team B #7（非原始 SVG）。

## MAIN 09 / 第 10 頁：AI 技術架構
**模型負責理解；真實世界，交給可信資料。**
- 使用者同意 → 來源與時效檢查 → 具確定性的推播硬門檻 → 候選 Jev 與 baseline 比較 → LLM 解析意圖／調用工具 → 可信資料回傳 route/ETA/fare → schema 檢查 → 使用者確認。
- **Jev = NOT TESTED。** 無真人評估、精準度、推論延遲或成本數據；若不能勝過規則式 baseline，就不用。
- 地圖／TDX／中央氣象署等為**可研究的候選**；非持有鑰匙或已串接。**官方 yoxi 私有 API 未授權。**
- 視覺：六段矩形架構，輸出前分清模型建議與可查證外部數據。
- 依據：`docs/ARCHITECTURE.md`、Team C PR #6。

## MAIN 10 / 第 11 頁：五條可信任原則
**寧可不打擾，也不要用錯誤資料催人搭車。**
1. 同意：位置／行事曆／通知漸進授權。
2. 節制：靜音、去重、冷卻、退訂。
3. 資料可信：來源、時間、過期就降級。
4. 安全：LLM 不猜 ETA、雨況、車資、已叫到車。
5. 控制權：真實叫車／付款須人類明確確認。
- 無可信資料時明確表示資訊不可用。
- 視覺：五行清晰護欄表。依據：產品 brief / architecture。

## MAIN 11 / 第 12 頁：競品差異化
**不是「第一個 AI 地圖」，而是出門前的決策協作。**
- 既有 yoxi 已有常用旅程／叫車偏好，不能宣稱一鍵叫車是本案獨創。
- Google Maps Ask Maps 已提供 AI 對話探索。
- 和泰同集團去趣 chicTrip 已有 AI 行程整理／附近優惠類功能。
- 本案**提案**聚焦「經同意的出門前事件 → 進同一段對話 → 跨運具中立卡片 → 人類確認」的組合。不是世界首創；也不是競品缺乏某能力的排他證明。
- 視覺：四行比較矩陣，其他產品依公開主打功能描述。
- 依據：Team C #6；[yoxi](https://www.yoxi.app/passenger-tutorial)；[Google](https://blog.google/products-and-platforms/products/maps/ask-maps-immersive-navigation/)；[chicTrip](https://apps.apple.com/tw/app/去趣-chictrip/id6443825385)。

## MAIN 12 / 第 13 頁：商業成長模型
**先創造日常價值，才有自然發生的叫車機會。**
- 價值：不是叫車日也能協助出行 → 信任：中立不騷擾 → 關係：持續有效互動 → 交易：有需求時回到原既有流程。
- 不是另立訂閱費，也不擅自假設和泰的抽成比例。**這是成長假說，沒有已證實的收入 uplift。**
- 視覺：四階段浮卡與底部「自願轉換」橫條。依據：產品 brief。

## MAIN 13 / 第 14 頁：KPI 與對照實驗
**高頻，不等於高打擾。**
- 北極星：每位週活用戶的**有效互動天數**。
- 品質：有價值提醒 Precision；同時追查漏報。
- 產品護欄：通知退訂／忽略／負面回饋。
- 商業結果：AI 協助後自願叫車率與重複使用（需追真正交易）。
- 實驗：規則提醒 baseline 與規則＋AI 建議對照；定義「有價值」，真人盲標、分組、設定前置 stop condition。**所有變化值尚未量測**。
- 視覺：四行 KPI 表＋實驗黑條。依據：產品 brief。

## MAIN 14 / 第 15 頁：落地路線與風險
**先驗證可信，再談規模化。**
- 現在／初賽：四幕模擬概念、來源契約、講述與安全意圖。
- PoC：8+ 合成案例、硬門檻／重複／過期偵測、LLM 卡片 schema。
- 授權合作：正式合作資料來源與 yoxi 接口、真人使用者試驗。
- 再擴展：成本、安全、可靠性、品牌授權、回退。
- Stop gates：官方 API 權限／資料刷新／個資授權／真實 booking 確認／Jev baseline／成本安全。
- 視覺：四列分期卡＋紅色 gate 條。依據：`docs/ARCHITECTURE.md`、Team C #6。

## MAIN 15 / 第 16 頁：結語
**把「搭不搭車」的決定，放在「叫車」之前。**
- 對使用者：不搭車也能得到有用建議。
- 對 yoxi：用可信日常互動，創造自願回訪與交易機會。
- 視覺：深綠強字收尾；全頁保留「提案／功能待驗證・畫面／價格均 [模擬]」標示。
- 講者：高頻不是逼每個人搭車，而是先讓品牌真的有用。
